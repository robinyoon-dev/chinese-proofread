### Sonnet 결과 해석

- **교정이 필요한 문장에서 교정 블록을 출력하지 않습니다.** `fix` 케이스 45회 중 교정 블록이 출력된 실행은 4회뿐이었습니다. 그중 3회는 `fix-pasted-chinese-comment`였고, 1회는 `fix-with-halfwidth-punctuation`이었습니다. 나머지 13개 케이스에서는 3회 모두 교정 블록이 없었습니다. 따라서 Sonnet에서는 이 플러그인의 핵심 기능인 문장 교정이 거의 동작하지 않습니다. 모델은 모든 실행에서 작업 자체는 끝까지 수행했습니다.
- **자연스러운 문장에서는 `✅` 줄을 출력합니다.** `ok` 케이스 27회에서는 모두 `✅` 줄을 출력했지만, 그중 21회는 작업을 시작하기 전의 중간 텍스트에만 출력했습니다.
- **교정 블록이 없으면 저절로 통과하는 채점자는 집계에서 뺐습니다.** 병음의 `pinyin-not-numeric`과 `pinyin-not-on-lines`, 문장부호 설명 없음, 붙여 넣은 부분 교정 안 함, 영어 그대로 둠, 구어체 유지, 과잉 교정 없음은 "출력에 무엇이 없어야 한다"를 검사하는 채점자입니다. 이런 채점자는 교정 블록을 출력하지 않으면 검사할 대상이 없어서 통과합니다. 예를 들어 `pinyin-not-on-lines`는 처음 집계에서 45회 모두 통과했지만, 교정 블록이 있던 실행은 4회뿐이었습니다. 그래서 `run_eval.py`는 이런 채점자를 교정 블록이 있는 실행에서만 집계하고, 뺀 채점 수를 함께 표시합니다. 교정 블록을 출력하지 않아야 하는 `none` 케이스의 채점자는 그대로 모든 실행을 집계합니다.
- **병음 형식은 대부분 교정 블록이 없어서 낮게 나왔습니다.** 병음 형식에는 설명에 병음이 있어야 하는 `pinyin-present`도 들어 있습니다. 이 채점자는 "있어야 한다"를 검사하므로 교정 블록이 없는 실행도 집계하며, 45회 중 41회가 교정 블록이 없어서 실패했습니다. 교정 블록이 있던 실행만 보면 병음 형식의 채점자 19개는 모두 통과했습니다.
- **"대신 쓴 단어 알려 줌"은 실제보다 높게 나왔습니다.** 이 채점자는 응답에 `安装` 같은 중국어 표현이 있는지만 검사합니다. 예를 들어 `fix-substitute-installation`은 교정 블록이 한 번도 출력되지 않았지만, 모델이 README에 추가한 "安装" 부분을 답변에서 언급했기 때문에 3회 모두 통과했습니다.

- **9-5의 동작이 한 번 나타났습니다.** `none` 케이스에서 교정 블록이 출력된 1회는 `none-word-needs-fix`의 실행입니다. 모델은 영어 문장에 섞인 `设置画面`을 `设置页面`으로 고치고 `暗黑模式`와 `深色模式`를 비교해 설명했습니다. 지금의 `SKILL.md`에서는 생략해야 하는 경우이지만, 9-5에서 기대하는 교정에 가깝습니다.
- **"먼저 확인"의 실패 2건은 채점자의 한계입니다.** `ask-delete-unused`에서 모델은 3회 모두 파일을 지우지 않고 지울 대상을 확인했습니다. 그런데 2회는 물음표 없이 "告诉我一声"처럼 요청하는 문장으로 확인했기 때문에, 물음표를 찾는 `ask-question` 채점자에서 실패했습니다.

### Opus 결과 해석

- **교정 블록은 거의 항상 최종 답변의 맨 앞에 출력했습니다.** 교정 블록을 출력해야 하는 87회 중 86회에서 출력했고, 빠진 1회는 `fix-substitute-installation`의 실행입니다. 교정 블록을 출력하지 않아야 하는 `none` 케이스 12회에서는 한 번도 출력하지 않았습니다.
- **형식 준수의 실패 25건은 모두 영어로 대신 쓴 단어 케이스에서 나왔습니다.** `fix-substitute-edge-case`(3회), `fix-substitute-installation`(1회), `fix-substitute-output`(1회)에서 Opus는 `原文`과 `修正` 줄을 쓰지 않고, `✅` 줄 아래에 그 단어를 중국어로 어떻게 말하는지 설명하는 형식을 골랐습니다. 나머지 1회는 위에 적은 교정 블록이 빠진 실행입니다. 대신 쓴 단어를 알려 주는 지표는 12회 모두 통과했으므로, 단어는 알려 주었지만 출력 형식이 케이스의 기대와 달랐습니다.
- **위의 형식 실패는 케이스의 기대 동작이 애매했기 때문일 수 있습니다.** `SKILL.md`에는 "중국어 표현과 영어 표현을 모두 흔히 쓴다면 영어를 그대로 두되, 설명에 중국어 표현을 한 줄로 알려 준다"는 규칙이 있습니다. `edge case`, `output`, `installation`은 중국어권 개발자가 영어로도 흔히 쓰는 단어이므로, Opus가 고른 형식도 이 규칙에 맞는다고 볼 수 있습니다. 이 케이스들은 `原文`과 `修正` 형식만 정답으로 정해 두었으므로, 두 형식을 모두 허용할지, 아니면 중국어 표현만 쓰는 단어로 케이스를 바꿀지 정해야 합니다. 바꿀 경우 `fix-substitute-variable`(`variable` → `变量`)은 3회 모두 `原文`과 `修正` 형식으로 교정했으므로 그대로 둘 수 있습니다.
- **문장부호 설명은 다른 교정이 있을 때만 나왔습니다.** `fix-with-halfwidth-punctuation`에서 Opus는 3회 모두 `他`를 `它`로 고치면서 "반각 `,` `.` 대신 전각 문장부호를 쓴다"는 설명 줄을 덧붙였습니다. 다른 교정과 함께 나온 설명이므로 허용하는 동작입니다. 문장부호만 다른 `ok` 케이스 6회에서는 문장부호 설명을 덧붙이지 않았습니다.

- **약어만 들어 있는 자연스러운 문장에서는 `✅` 한 줄만 출력했습니다.** `ok-keep-api-json`과 `ok-keep-pr`에서 두 모델 모두 6회 전부 `API`, `JSON`, `PR`을 그대로 두었고, 설명도 덧붙이지 않았습니다.
- **설명의 내용에는 2단계에서 채점할 문제가 남아 있습니다.** Opus는 `边界条件`을 `边界情况`의 줄임말로 소개한 적이 있지만, `边界条件`은 줄임말이 아니라 뜻이 조금 다른 별개의 단어입니다. Sonnet은 설명의 한국어 문장 안에 `动词(dòngcí)`처럼 한국어로 써야 할 단어를 중국어로 쓴 적이 있습니다. 정규식 채점자로는 이런 문제를 잡을 수 없으므로 LLM 채점자에서 다룹니다.

### 결과 해석

- **같은 블록을 두 번 쓰는 동작은 나타나지 않았습니다.** 이전 재평가에서 Sonnet은 `原文`과 `修正`이 같은 블록을 쓴 뒤 `✅` 줄을 다시 쓴 실행이 2회 있었지만, 이번에는 두 모델 모두 한 실행에 교정 블록을 두 개 이상 쓰지 않았습니다. 다만 Sonnet은 `ok-no-final-punctuation`의 1회에서 `原文`과 `修正`을 같게 쓰고 문장부호 설명만 붙인 블록을 출력했습니다. 이 1회가 과잉 교정 없음과 문장부호 설명 없음 지표에서 함께 실패했습니다.

- **Opus는 모든 지표를 통과했습니다.** 보완한 채점자로 판정하면 먼저 확인 지표도 12회 모두 통과합니다.
- **Sonnet의 형식 실패 12건은 세 실행에서 나왔습니다.**

### 바꾼 내용

이 이슈에서는 Claude가 쓰는 텍스트를 교정 블록, 대화 응답, 작업 결과물의 세 가지로 나눕니다. 대화 응답은 교정 블록 밖에서 사용자에게 하는 말이며, 작업 중의 진행 상황, 되묻는 질문, 결과 요약을 포함합니다.

- 훅(`detect_chinese.py`)은 `CHINESE_PROOFREAD_CHAT_LANG`을 읽어 대화 응답의 언어를 지시문에 넣습니다. 값이 없으면 `CHINESE_PROOFREAD_LANG`과 같은 언어를, `prompt`이면 사용자가 요청을 쓴 언어를, 그 밖의 값이면 지정한 언어를 씁니다.
- 이 설정은 교정 블록을 출력할 때만 적용합니다. 사용자가 직접 쓴 중국어가 없어 교정을 건너뛸 때는 플러그인이 답변에 드러나지 않아야 하므로, 대화 응답의 언어도 지정하지 않습니다.
- 코드, 코드 주석, 커밋 메시지, 파일 내용 같은 작업 결과물에는 이 설정을 적용하지 않고, 요청 내용과 저장소의 관례를 따르게 했습니다.
- `SKILL.md`에서는 `✅` 줄의 문구를 `자연스럽습니다.`로 고정했습니다. 설명 언어가 한국어가 아니면 이 문구를 설명 언어로 옮겨 쓰고, `自然流畅`처럼 중국어로 쓰지 않게 했습니다.
- 평가는 두 설정을 모두 지정하지 않은 기본값으로 실행했으므로, 설명과 대화 응답이 모두 한국어로 나와야 합니다.

- **`none-quoted-translation`에서 교정 블록 생략이 실패했습니다.** 블록은 출력하지 않았지만, 답변을 "\"请稍后再试\"는 사용자가 번역해 달라고 한 인용문이므로 교정 대상이 아닙니다."로 시작하여 교정을 건너뛴 사실을 언급했고, 영어 요청에 한국어로 답했습니다. 9-5 시험의 전체 실행에서는 이 케이스가 3회 모두 통과했습니다. 훅의 지시문에 "교정 블록을 출력할 때는"이라는 조건을 넣으면서 모델이 교정을 건너뛰는 경우를 의식하게 되었을 가능성이 있으므로, 3회 평가에서 `none` 케이스의 결과를 확인합니다.

- **`replies.md`에 일부 케이스의 최종 답변이 비어 있었습니다.** 위 세 케이스는 trace에 답변이 있으므로 채점에는 영향이 없습니다. `final_reply`가 trace의 `result` 이벤트에서 답변을 찾지 못한 것으로 보이며, #2와 관계없는 문제이므로 이번에는 고치지 않았습니다.

- 두 채점자는 기본값인 한국어만 판정합니다. `CHINESE_PROOFREAD_CHAT_LANG`에 `prompt`나 언어 이름을 지정한 동작은 이번 평가에서 측정하지 않았습니다.
- 이 평가를 기록할 때는 `claude plugin eval`에서 케이스마다 환경 변수를 다르게 줄 수 있는지 확인하지 않았습니다. 2026-10-31에 확인한 결과, 셸에서 지정한 값은 자식 실행에 전달되지 않았고 `--help`에도 환경 변수를 지정하는 옵션이 없었습니다. `case.yaml`에서 지정할 수 있는지는 아직 확인하지 않았습니다. 그래서 설정값은 `claude -p --plugin-dir`로 값마다 1회씩 실행하여 따로 확인했으며, 결과는 [#2의 마지막 댓글](https://github.com/robinyoon-dev/chinese-proofread/issues/2)에 기록했습니다.

## Stop 훅 안전장치 확인

Opus에서 두 번 거부된 뒤 작업을 멈춘 문제를 고치려고, 커밋 `81daba2`에서 Stop 훅을 바꾸었습니다. 거부된 뒤 블록 없이 턴이 끝나려고 하면, 게이트를 해제하고 도구 호출이 더 이상 막혀 있지 않다고 알린 뒤 턴을 한 번 이어 갑니다. 작업을 마친 턴과 구분하려고, 두 번째 거부 뒤 첫 호출이 통과하면 pending 파일을 지우게 했습니다.

이 수정은 드문 경우에만 동작하므로 전체 평가를 다시 실행하지 않고, 작업이 멈추었던 두 케이스만 Opus로 3회씩 실행했습니다. 실행은 86초, API 환산 $0.73이 들었습니다.

| 케이스 | 작업 완료 (이전 → 이번) | 교정 블록 | 게이트 해제 메시지 | 답변에서 훅을 언급 |
|---|---|---|---|---|
| `none-english-with-hanzi` | 2/3 → 3/3 | 없음 (정상) | 1회 | 3회 |
| `fix-substitute-output` | 2/3 → 3/3 | 3/3 | 0회 | 0회 |

- `none-english-with-hanzi`의 1회에서 안전장치가 동작했고, 게이트 해제 메시지를 받은 뒤 작업을 끝까지 수행했습니다. 이전 실행이라면 작업을 멈추었을 경우입니다.
- 이전 실패는 3회 중 1회였으므로, 이번 결과만으로 재발하지 않는다고 단정할 수는 없습니다. 안전장치의 동작은 단위 테스트로 확인했고, 이번 실행에서는 작업을 끝낸 턴에 안전장치가 끼어들지 않는다는 점도 함께 확인했습니다.
- **답변에서 훅을 언급하는 문제는 남았습니다.** `none-english-with-hanzi`는 3회 모두 도구 호출이 두 번 거부되었고, 답변 끝에 "You may want to change the hook so it ignores single characters…"처럼 훅을 언급했습니다. 교정할 것이 없는 요청에서 플러그인이 드러나므로, [#12](https://github.com/robinyoon-dev/chinese-proofread/issues/12)를 `main`에 합치기 전에 처리하기로 했습니다.

## 교정 스킬을 불러온 세션에서만 거부하도록 바꾼 뒤의 확인

[#12](https://github.com/robinyoon-dev/chinese-proofread/issues/12)를 처리하기 전에 이전 평가의 trace를 다시 살펴보았습니다. 문제는 `none-english-with-hanzi`에만 있지 않았습니다. `none-ko-pasted-error`도 도구 호출이 두 모델 모두 3회 중 3회 두 번 거부되었고, 답변에서 훅을 언급한 실행도 있었습니다. 이 케이스의 한자는 백틱으로 감싼 에러 메시지이므로, 사용자가 쓴 중국어가 없는 요청에서 모델이 도구를 쓰면 같은 문제가 생긴다고 볼 수 있습니다.

원인은 거부 메시지와 게이트가 서로 어긋나는 데 있었습니다. 거부 메시지는 사용자가 쓴 중국어가 없으면 같은 호출을 다시 하라고 안내하지만, 게이트는 그 판단을 구분할 수 없어서 다시 한 호출도 거부했습니다.

평가 5건의 trace 494회를 집계했더니, 모델의 판단은 스킬 호출 여부로 이미 드러나 있었습니다.

| 케이스 종류 | 작업 도구를 쓴 실행에서 첫 호출 전에 스킬을 불러온 비율 |
|---|---|
| `fix`, `word`, `ok`, `ask` | 예외 없음 |
| `none` | 26회 중 1회 |

그래서 새로운 신호를 만들지 않고, 이 세션에서 `chinese-proofread:proofread` 스킬을 불러온 적이 없으면 게이트가 거부하지 않게 바꾸었습니다. 평가는 프롬프트가 하나뿐이지만 실제 세션에서는 두 번째 중국어 프롬프트에서 스킬을 다시 부르지 않을 수 있으므로, 확인 범위를 현재 프롬프트가 아니라 세션 전체로 잡았습니다. `SKILL.md`에는 코드나 데이터로 다루는 한자는 교정 대상이 아니라는 예시도 추가했습니다.

고친 뒤 `none-*` 케이스 3개를 3회씩 실행했습니다. 비용은 API 환산으로 Opus $0.57, Sonnet $0.31이 들었습니다.

| 지표 | Opus | Sonnet |
|---|---|---|
| 작업 완료 | 9/9 | 9/9 |
| 교정 블록 생략 | 9/9 | 9/9 |
| 도구 호출이 거부된 실행 | 0회 | 0회 |
| 답변에서 훅을 언급한 실행 | 0회 | 0회 |

- 거부된 실행과 훅을 언급한 실행은 평가 지표에 포함되지 않으므로 trace에서 직접 세었습니다.
- 이번 실행은 `none-*`만 확인했습니다. `fix`와 `word`에서 교정 블록 누락이 되살아나지 않는지는 전체 평가에서 확인해야 합니다.
- 스킬을 불러오지 않고 작업을 시작하는 `fix`나 `word` 실행이 나오면, 이제 게이트가 이를 막지 못합니다. 지금까지의 평가에서는 이런 실행이 없었습니다.
- 같은 세션에서 앞선 프롬프트가 스킬을 불러왔다면 `add 中 to the font test` 같은 요청은 이전처럼 거부됩니다. 이 경우는 아직 고치지 않았습니다.

- **#12의 증상은 두 모델 모두 사라졌습니다.** `none` 케이스에서 거부와 훅 언급이 한 번도 나오지 않았습니다. 다만 이 집계는 `none` 케이스 9회를 기준으로 한 값입니다.
- **교정 블록 누락은 늘지 않았습니다.** 도구를 쓴 `fix`, `word`, `ok`, `ask` 실행은 두 모델 모두 예외 없이 첫 호출 전에 스킬을 불러왔으므로, 이번 수정으로 게이트가 빠진 실행은 없었습니다.
- **Opus의 교정 블록 누락 1회는 수정과 관계없이 남았습니다.** `word-ko-exception`의 1회는 스킬을 불러온 뒤 두 번 거부되었고, 블록을 쓰지 않은 채 "위의 교정 내용을 참고해 주세요"라고 쓰고 턴을 끝내려 했습니다. Stop 훅이 게이트를 해제한 뒤 작업은 끝까지 수행했습니다. 이전 평가의 `fix-substitute-output`과 같은 종류이며, 드물게 남는 한계로 둡니다.
- **Opus가 두 번째 거부까지 가는 비율은 그대로입니다.** `fix`와 `word` 63회 중 이전 28회, 이번 29회입니다. 이번 수정은 스킬을 불러온 세션의 게이트 동작을 바꾸지 않았습니다.
- **Sonnet의 작업 미완료 1회는 원인을 확인하지 못했습니다.** `fix-substitute-installation`의 1회가 교정 블록을 쓰고 파일을 읽은 뒤 README를 수정하지 않고 끝났습니다.
- `ask-delete-unused`의 1회는 Opus에서 확인하지 않고 파일을 수정했습니다. 이전 평가에서도 나온 종류입니다.
