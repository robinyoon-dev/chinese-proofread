# 교정 품질 평가 1회 점검 실행

이 문서는 `TODO.md`의 6-3에서 1단계 평가 세트를 만든 뒤, 기준 점수를 기록하기 전에 케이스와 채점자를 점검하려고 한 번씩 실행한 결과를 기록합니다. 케이스마다 1회만 실행했고, 이 실행에서 발견한 문제로 케이스와 채점자를 고쳤으므로, 이 문서의 수치는 기준 점수로 쓰지 않습니다. 기준 점수는 고친 평가 세트를 케이스마다 3회 실행하여 `docs/eval-results.md`에 기록합니다.

- **날짜**: 2026-10-29
- **대상 커밋**: `eed23cd` (플러그인 파일은 `d44b72d`와 같습니다)

## 평가 세트

평가 세트는 `evals/quality/cases.py`에 정의했고, `evals/quality/run_eval.py`가 플러그인을 임시 폴더에 복사한 뒤 그 복사본 안에 `claude plugin eval`의 케이스 폴더를 만들어 실행합니다. 이 점검 실행에서 사용한 케이스는 34개입니다.

| 종류 | 케이스 수 | 기대하는 동작 |
|---|---|---|
| `fix` | 15 | 오류가 있는 문장입니다. `原文`, `修正`, `설명`이 있는 교정 블록을 출력해야 합니다. 구어체, 반각 문장부호, 붙여 넣은 코드, 영어로 대신 쓴 단어가 들어 있는 케이스를 포함합니다. |
| `ok` | 9 | 자연스러운 문장입니다. `✅` 한 줄만 출력해야 합니다. 반각 문장부호와 붙여 넣은 로그가 들어 있는 케이스를 포함합니다. |
| `note` | 4 | `bug`, `API`, `commit`, `PR`처럼 영어로 그대로 쓰는 단어가 들어 있는 자연스러운 문장입니다(9-4). `✅` 줄을 출력하고 영어 단어를 바꾸지 않아야 합니다. |
| `ask` | 2 | 해석이 갈리는 요청입니다. 파일을 고치기 전에 먼저 확인해야 합니다. |
| `none` | 4 | 사용자가 직접 쓴 중국어 문장이 없는 입력입니다. 교정 블록을 출력하지 않아야 합니다. 9-5에서 다루는 중국어 단어 케이스 2개를 포함합니다. |

Bash를 허용할 수 없으므로(`docs/eval-6-3/pilot.md` 참고), 모든 케이스는 `Read`, `Edit`, `Write`만으로 끝나는 작업으로 만들었습니다.

### 교정 블록이 출력된 위치

두 모델의 형식 준수율이 크게 다른 이유를 확인하려고, 교정 블록이 최종 답변에 있었는지와 응답의 텍스트 블록 중 어디에라도 있었는지를 케이스 종류별로 나누어 집계했습니다. 표의 값은 교정 블록이 출력된 케이스 수입니다. "텍스트 블록 어디든"의 값은 아래 "고친 문제"에 적은 줄바꿈 문제를 고친 패턴으로, 저장해 둔 실행 기록을 다시 검사하여 확인했습니다. 고치기 전의 패턴으로 집계한 값과 같았습니다.

| 종류 | Sonnet: 최종 답변 | Sonnet: 텍스트 블록 어디든 | Opus: 최종 답변 | Opus: 텍스트 블록 어디든 |
|---|---|---|---|---|
| `fix` (15개) | 1 | 1 | 15 | 15 |
| `ok` (9개) | 3 | 9 | 7 | 8 |
| `note` (4개) | 0 | 2 | 4 | 4 |
| `ask` (2개) | 0 | 0 | 2 | 2 |

- Sonnet은 케이스 종류에 따라 두 가지로 다르게 동작했습니다.
  - `fix` 케이스에서는 15개 중 14개에서 교정 블록을 아예 출력하지 않았습니다. 시범 실행에서는 이런 경우에 교정 판단이 도구를 호출하는 사이의 진행 메모에만 남았습니다. 이번 실행의 진행 메모는 케이스마다 확인하지 않았습니다.
  - `ok` 케이스에서는 9개 모두 `✅` 줄을 출력했지만, 그중 6개는 작업을 시작하기 전의 중간 텍스트에 출력했고 최종 답변에서는 빠졌습니다.
- Opus는 거의 모든 케이스에서 최종 답변의 맨 앞에 교정 블록을 출력했습니다. 예외는 두 케이스였습니다.
  - `ok-add-comment`에서는 `✅` 줄을 중간 텍스트에만 출력했습니다.
  - `ok-colloquial`에서는 교정 블록을 출력하지 않았습니다. 이 케이스의 문장은 아래 "고친 문제"에 적은 대로 두 가지로 읽히는 문장이었습니다.
- 대화형 세션에서는 도구 호출 사이의 중간 텍스트도 사용자에게 표시되므로, 중간 텍스트에 출력한 `✅` 줄은 사용자가 볼 수 있을 가능성이 높습니다. 반면 진행 메모는 표시되는지 확인하지 않았습니다. eval은 `claude -p`처럼 최종 답변만 보는 방식으로 채점하므로, 이 차이는 아직 확인이 필요합니다.
- `SKILL.md`는 교정 결과를 "응답의 맨 앞에" 출력하라고 지시합니다. 작업 전의 중간 텍스트도 응답의 맨 앞이므로, 최종 답변만 기준으로 삼으면 실제보다 엄격하게 채점할 수 있습니다.

### 채점 기준 변경

위의 이유로, 답변을 검사하는 채점자는 최종 답변이 아니라 응답의 모든 텍스트 블록을 기준으로 채점하기로 했습니다. 교정 블록이 텍스트 블록 중 어디에라도 있으면 통과로 봅니다.

- eval의 `regex` 채점자는 최종 답변(`last_message`)이나 JSON 형식의 실행 기록 전체(`trace`)만 검사할 수 있습니다. 실행 기록 전체에는 모델이 불러온 `SKILL.md`의 출력 예시(`原文: …`)도 들어 있어서, 실행 기록을 그대로 검사하면 모델이 교정 블록을 출력하지 않아도 통과할 수 있습니다.
- 그래서 `run_eval.py`가 저장해 둔 실행 기록에서 모델이 쓴 텍스트 블록만 모은 뒤, 최종 답변을 검사하던 채점자의 패턴을 그 텍스트에 다시 적용합니다. 도구 호출 횟수와 파일 내용을 검사하는 채점자는 eval의 판정을 그대로 씁니다.
- eval이 최종 답변으로 채점한 결과는 보조 지표로 함께 기록합니다. `claude -p`처럼 최종 답변만 보여 주는 환경에서는 이 지표가 사용자가 보는 결과에 더 가깝기 때문입니다.

이 점검 실행은 실행 기록을 저장해 두었으므로, 모델을 다시 호출하지 않고 바뀐 기준으로 다시 채점했습니다. 값이 달라진 지표는 형식 준수뿐이었습니다.

| 형식 준수 | Sonnet 5.5 | Opus 5.5 |
|---|---|---|
| 모든 텍스트 블록 기준 (주 지표) | 0.167 (15/90) | 0.989 (89/90) |
| 최종 답변 기준 (보조 지표) | 0.089 (8/90) | 0.978 (88/90) |

바뀐 기준으로도 Sonnet의 형식 준수율이 낮은 이유는, `fix` 케이스의 교정 블록 5개 항목(`format-block-first`, `format-original`, `format-fixed`, `format-explain`, `format-end`)이 15개 중 14개 케이스에서 모두 실패했기 때문입니다. 이 케이스들은 교정 블록이 어느 텍스트 블록에도 없었습니다.

### 사용 한도

실행 기록에 남은 사용률을 보면, 두 모델의 실행을 동시에 진행하는 동안 5시간 한도의 사용률은 3%에서 4%로, 주간 한도의 사용률은 9%에서 10%로 올랐습니다. 사용률이 1% 단위로 기록되므로 정확한 사용량은 알 수 없습니다. 이 값을 기준으로 하면, 케이스마다 3회씩 두 모델로 실행하는 기준 점수 실행(API 환산 약 $15)은 5시간 한도의 약 3~5%를 사용할 것으로 예상합니다.

## 고친 문제

점검 실행에서 발견한 케이스와 채점자의 문제는 다음과 같으며, 모두 고쳤습니다.

- **프런트매터에 들어간 `---`**: `format-end` 채점자의 패턴 `^---\s*$`를 eval이 프런트매터의 끝으로 읽어서, 첫 실행에서 `fix` 케이스 15개를 불러오지 못했습니다. 패턴을 `^-{3}\s*$`로 바꾸었습니다. 위의 결과는 이 문제를 고친 뒤에 실행한 결과입니다.
- **도구를 호출하지 않았는지 확인하는 채점자**: `tool_used` 채점자에 `max: 0`만 지정하면 `min`이 기본값 1로 남아서, 도구를 한 번도 호출하지 않아도 실패로 판정했습니다. `min: 0`을 함께 지정했습니다.
- **`Edit` 호출 횟수로 수정 여부를 확인한 채점자**: 모델이 `Write`로 파일 전체를 다시 쓰는 경우가 있으므로, `fix-substitute-variable`에서는 파일 내용을 검사하도록 바꾸었습니다.
- **두 가지로 읽히는 `ok` 문장**: `ok-colloquial`의 `这个函数咋老多算1啊？`에서 `老多`는 "늘"이 아니라 "아주 많이"로도 읽힙니다. Sonnet이 이 부분을 `老是`로 고친 것은 타당한 교정이었으므로, 문장을 `老是多算1`로 바꾸었습니다.
- **해석이 갈려도 위험이 작은 `ask` 케이스**: 처음에 만든 `帮我把utils.py里的函数都改成英文的`와 `把average改成median的`에서는 두 모델 모두 합리적인 해석을 하나 골라 작업했고, Opus는 다른 해석의 가능성을 설명에 덧붙였습니다. 잘못 해석해도 쉽게 되돌릴 수 있는 수정이므로, 먼저 묻지 않고 작업한 것을 실패로 보기 어렵습니다. 두 케이스를 빼고, 잘못 해석하면 파일을 지울 수 있는 `帮我把没用的都删了` 케이스로 바꾸었습니다. 바꾼 케이스를 Sonnet으로 실행했을 때, 모델은 지울 후보를 찾은 뒤 지우기 전에 먼저 확인했습니다.
- **실행 기록이 남지 않는 문제**: eval의 결과 파일에는 모델의 답변이 남지 않고, eval은 실행이 끝나면 작업 폴더를 지웁니다. 실패한 채점자만으로는 모델이 실제로 무엇을 출력했는지 알 수 없으므로, `run_eval.py`가 각 실행의 `trace.jsonl`과 최종 답변을 결과 폴더의 `traces/`와 `replies.md`에 저장하도록 했습니다.
- **줄바꿈으로 시작하는 답변**: `diag-block-in-text` 채점자는 JSON 형식의 실행 기록을 검사하므로, 텍스트 블록이 줄바꿈으로 시작하면 줄바꿈이 `\n` 두 글자로 기록되어 패턴이 맞지 않습니다. 이 경우에도 교정 블록을 찾도록 패턴을 고쳤습니다.

고친 결과, 기준 점수에 사용할 평가 세트는 케이스 33개입니다.
