# 설계 결정 기록

이 문서는 플러그인을 만들면서 내린 설계 결정과 그 이유를 기록합니다. 결정마다 고려한 대안과 감수한 트레이드오프를 함께 적어서, 나중에 결정을 다시 검토하거나 다른 사람에게 설명할 때 근거로 쓸 수 있게 합니다.

지금 구조를 요약한 글은 [설계와 평가](design-and-evaluation.md)에 있습니다. 이 문서는 결정을 내린 순서대로 내용을 쌓았으므로, 뒤의 결정이 앞의 결정을 바꾼 경우가 있습니다.

19번 항목에 따라 교정은 `proofread` 스킬이 아니라 별도 프로세스가 맡습니다. 1, 3, 4, 14번 항목에 나오는 스킬과 훅 지시문의 설명은 당시 구조를 기준으로 합니다. 판별을 코드로 처리하고 판단이 필요한 일을 모델에 맡기는 원칙은 그대로입니다.

새로운 결정을 내리면 아래 형식에 맞춰 항목을 추가합니다.

- **결정**: 무엇을 어떻게 하기로 했는지 씁니다.
- **이유**: 그렇게 결정한 근거를 씁니다.
- **대안**: 검토했지만 선택하지 않은 방법과, 선택하지 않은 이유를 씁니다.
- **트레이드오프**: 이 결정 때문에 감수하게 된 한계를 씁니다.

기록할 때는 다음 규칙을 지킵니다.

- 이슈를 진행하면서 새로운 결정을 내리면, 결정과 이유와 대안과 트레이드오프를 그 자리에서 추가합니다. 시간이 지나면 검토했던 대안을 잊어버리기 쉬우므로 미루지 않습니다.
- "대안"에는 실제로 검토했던 방법만 적습니다.
- 평가 결과가 나오면 관련된 결정 항목에 수치를 근거로 덧붙입니다.

`TODO.md`는 삭제했으며, 남은 작업은 GitHub 이슈로 관리합니다. `docs/`의 문서와 평가 코드에서 `TODO.md`의 번호(예: 6-3, 9-5)로 언급한 항목은 모두 [커밋 `b768c62`의 `TODO.md`](https://github.com/robinyoon-dev/chinese-proofread/blob/b768c62/TODO.md)를 가리킵니다. 그 버전에는 완료한 작업의 진행 기록과 남은 작업의 세부 계획이 들어 있습니다.

## 1. 언어 판별은 훅에서 코드로 처리하고, 교정은 스킬에서 모델이 처리한다

- **결정**: 입력이 중국어인지 판별하는 작업은 `UserPromptSubmit` 훅에서 실행하는 Python 스크립트(`detect_chinese.py`)가 맡습니다. 문장을 교정하는 작업은 `proofread` 스킬의 지시에 따라 모델이 맡습니다.
- **이유**: 판별은 매 입력마다 실행되므로 비용이 들지 않고 결과가 항상 같아야 합니다. 글자의 유니코드 범위를 세는 규칙만으로도 충분히 판별할 수 있으므로 모델을 쓸 필요가 없습니다. 반면 문장이 원어민에게 자연스러운지 판단하는 일은 규칙으로 처리할 수 없으므로 모델에 맡깁니다.
- **대안**:
  - 스킬의 `description`만 두고 모델이 스스로 스킬을 호출하게 하는 방법이 있습니다. 하지만 이 방법으로는 모델이 스킬을 호출하지 않고 바로 작업을 시작할 수 있어서, 교정이 항상 실행된다고 보장할 수 없습니다.
  - 모든 입력에 "중국어라면 교정하라"는 지시를 붙이는 방법도 있습니다. 하지만 이 방법을 쓰면 중국어가 아닌 입력에도 매번 지시문만큼 토큰을 소비하고, 판별 결과도 모델에 따라 달라집니다.
- **트레이드오프**: 판별 규칙이 단순하기 때문에 문맥을 고려하지 못합니다. 예를 들어 가나 없이 한자로만 쓴 짧은 일본어 문장은 중국어로 판별됩니다.

## 2. 판별 규칙은 한자 수, 가나 포함 여부, 한자와 한글의 비율로 정한다

- **결정**: 다음 세 조건을 모두 만족하면 중국어로 판별합니다.
  - 한자가 `CHINESE_PROOFREAD_MIN_HANZI`(기본값 4)자 이상 있습니다.
  - 히라가나나 가타카나가 하나도 없습니다.
  - 한자 수와 한글 수를 더한 값에서 한자가 차지하는 비율이 `CHINESE_PROOFREAD_HANZI_RATIO`(기본값 0.5) 이상입니다.
  - 2026-10-30에 14번 항목에 따라 바꾸었습니다. 영문자나 한글이 섞인 입력에는 `CHINESE_PROOFREAD_MIN_HANZI_MIXED`(기본값 1)를 적용하고, 비율의 기본값은 0으로 낮추었습니다. 아래의 이유와 트레이드오프는 바꾸기 전의 기본값(4 / 1 / 0.5)에 대한 기록입니다.
- **이유**:
  - 최소 한자 수를 두면 한국어 문장에 섞인 한자 한두 글자 때문에 오판하는 경우를 막을 수 있습니다.
  - 일본어 문장에는 거의 항상 가나가 들어가므로, 가나가 있으면 일본어로 보고 제외합니다.
  - 비율을 계산할 때 라틴 문자를 분모에 넣지 않았습니다. 개발 작업을 요청하는 문장에는 코드와 식별자가 많이 섞이는데, 라틴 문자를 포함하면 중국어 문장도 비율 조건을 통과하지 못하기 때문입니다.
- **대안**: 언어 감지 라이브러리를 쓰는 방법이 있습니다. 하지만 외부 패키지를 설치해야 하므로 플러그인을 설치하는 과정이 복잡해지고, 코드가 섞인 짧은 문장에서는 오히려 정확도가 낮을 수 있습니다.
- **트레이드오프**:
  - 2026-10-29에 `TODO.md`의 6-2에서 기본값을 측정했습니다. 확인용 세트에서 재현율은 0.909(20/22), 오탐률은 0.467(7/15)이었습니다. 측정 방법과 전체 수치는 `docs/eval-results.md`에 기록했고, 설정값을 고른 기준은 12번 항목에 기록했습니다.
  - 측정한 360개 조합 중에서 기본값보다 재현율과 오탐 수가 모두 나은 설정은 없었으므로 기본값을 유지했습니다. 다른 설정은 모두 재현율을 얻는 대신 오탐이 늘거나, 오탐을 줄이는 대신 재현율을 잃습니다.
  - 비율 기준을 낮추면 한국어로 대신 쓴 단어가 들어 있는 중국어 문장을 더 많이 잡지만, 중국어를 붙여 넣은 한국어 요청에도 반응합니다. 전체 데이터셋에서 3 / 1 / 0.3으로 바꾸면 `zh_korean_substitute`와 `zh_with_pasted_text`에서 5개를 더 잡습니다. 대신 `ko_with_pasted_chinese`에서 오탐이 4개 늘어나고, 현재 기준에서는 `ko_with_hanzi`의 `word` 문장 4개도 오탐이 되므로 모두 8개가 늘어납니다.
  - 오탐은 대부분 영어 요청에 한자가 섞인 문장과 한국어 요청에 중국어를 붙여 넣은 문장에서 발생합니다. 한자가 없는 한국어 요청과 영어 요청에서는 오탐이 없었습니다.

## 3. 훅은 판별 결과를 `additionalContext`로 전달한다

- **결정**: 훅은 중국어를 감지하면 `hookSpecificOutput.additionalContext`에 스킬을 적용하라는 지시를 담아 출력합니다. 중국어가 아니면 아무것도 출력하지 않습니다.
- **이유**: `UserPromptSubmit` 훅은 사용자의 입력을 바꿀 수 없고, 컨텍스트를 추가하거나 입력을 차단하는 일만 할 수 있습니다. 교정은 입력을 막는 기능이 아니므로 컨텍스트를 추가하는 방식을 씁니다. 이 방식을 쓰면 사용자가 쓴 원문도 그대로 모델에 전달됩니다.
- **트레이드오프**: 추가한 지시는 강제력이 없으므로, 모델이 지시를 따르지 않을 가능성이 남아 있습니다. 모델이 지시를 얼마나 잘 따르는지는 평가로 측정합니다.

## 4. 훅이 넓게 감지하고, 스킬이 교정할 대상을 걸러 낸다

- **결정**: 훅은 입력 전체를 대상으로 판별하므로, 사용자가 붙여 넣은 중국어 로그나 에러 메시지 때문에 중국어로 판별될 수 있습니다. 이런 경우는 스킬에서 처리합니다. 스킬은 사용자가 직접 쓴 문장만 교정하고, 교정할 대상이 없으면 교정 블록을 출력하지 않습니다.
- **이유**: 붙여 넣은 내용과 사용자가 쓴 문장을 구분하려면 문맥을 이해해야 하므로, 규칙보다 모델이 더 잘 판단합니다. 그래서 훅은 단순하게 유지하고, 문맥이 필요한 판단은 스킬로 넘깁니다.
- **트레이드오프**: 훅이 잘못 감지한 경우에도 지시문이 추가되므로 토큰이 조금 소비됩니다.
- **확장**: 2026-10-30에 14번 항목에서 이 원칙을 더 넓게 적용했습니다. 훅은 한자가 섞인 한국어와 영어 입력에도 반응하고, 사용자가 직접 섞어 쓴 단어인지 인용한 중국어인지는 스킬이 판단합니다.

## 5. 교정 결과를 먼저 보여 주고, 멈추지 않고 원래 요청을 수행한다

> 이 결정은 19번 항목으로 바뀌었습니다. 지금은 교정과 작업을 동시에 시작하며, 메인 모델은 원문을 기준으로 작업합니다. "멈추지 않고 수행한다"와 "해석이 갈리면 먼저 확인한다"는 유지합니다.

- **결정**: 교정 블록은 응답의 맨 앞에 정해진 형식(`📝 中文校对`)으로 출력합니다. 교정이 끝나면 교정된 의미를 기준으로 원래 요청을 바로 수행합니다. 다만 원문의 오류 때문에 요청이 여러 가지로 해석되고 해석에 따라 작업이 달라진다면, 작업을 시작하기 전에 사용자에게 확인합니다.
- **이유**: 사용자는 중국어를 연습하면서 실제 개발 작업도 처리하려고 합니다. 교정 때문에 작업 흐름이 끊기면 플러그인을 쓰지 않게 되므로, 교정은 부가 정보로 보여 주고 작업은 그대로 진행합니다. 출력 형식을 고정한 이유는 사용자가 읽기 쉽고, 나중에 `Stop` 훅이 transcript에서 교정 블록을 찾아 기록할 수 있게 하기 위해서입니다.
- **트레이드오프**: 교정이 틀렸는데 그 교정을 기준으로 작업하면 사용자의 의도와 다른 작업을 할 수 있습니다. 해석이 갈리는 경우에만 확인하도록 하여 이 위험을 줄였습니다.

## 6. 설정은 환경 변수로 받는다

- **결정**: 설명 언어, 대화 응답 언어, 최소 한자 수, 한자 비율은 환경 변수로 설정합니다.
- **이유**: 사용자가 `~/.claude/settings.json`의 `env` 항목에 값을 적기만 하면 되고, 훅 스크립트도 별도의 설정 파일을 읽지 않아도 됩니다.
- **트레이드오프**: 환경 변수를 바꾸면 Claude Code를 다시 시작해야 반영됩니다. 그래서 자주 바꾸는 켜기와 끄기 설정은 환경 변수가 아니라 상태 파일로 처리합니다(9번 항목).

## 7. 한자가 0자일 때 비율을 계산하지 않는다

- **결정**: 판별 조건에서 `hanzi == 0`을 가장 먼저 검사하여, 한자가 없으면 비율을 계산하기 전에 종료합니다(커밋 `19c1d9b`).
- **이유**: 기본 설정에서는 최소 한자 수 조건이 먼저 걸러 주지만, 사용자가 `CHINESE_PROOFREAD_MIN_HANZI`를 0으로 설정하면 한자도 한글도 없는 입력에서 0으로 나누는 오류가 발생했습니다. 훅에서 예외가 발생하면 사용자가 입력할 때마다 오류가 표시되므로, 설정값과 관계없이 안전하게 동작하도록 고쳤습니다.

## 8. 한어병음은 설명에 나오는 단어에만 붙인다

- **결정**: 교정 블록의 설명에서 중국어 단어나 구절을 언급할 때, 바로 뒤에 괄호로 한어병음을 덧붙입니다. 병음은 성조 부호로 표기하고 단어 단위로 띄어 씁니다. `原文`과 `修正` 줄에는 병음을 붙이지 않습니다.
- **이유**: 사용자는 중국어를 연습하는 중이므로, 교정 설명에 나온 단어를 바로 읽을 수 있어야 학습에 도움이 됩니다. 설명에 나오는 단어는 고친 부분의 핵심이므로, 그 단어에만 병음을 붙이면 출력이 크게 길어지지 않으면서도 필요한 발음 정보를 전달할 수 있습니다.
- **대안**:
  - `原文`과 `修正` 문장 전체에 병음을 붙이는 방법이 있습니다. 하지만 이 방법을 쓰면 두 줄이 길어지고 한자와 병음이 섞여서, 원문과 수정문에서 무엇이 바뀌었는지 비교하기 어려워집니다.
  - 성조를 숫자로 표기하는 방법(`ta1`)이 있습니다. 숫자 표기는 키보드로 입력하기 쉽지만, 사전과 교재에서 일반적으로 쓰는 표기는 성조 부호이고 읽을 때도 성조 부호가 더 직관적이므로 선택하지 않았습니다.
- **트레이드오프**: 병음은 모델이 생성하므로 다음자(多音字)나 성조 변화가 있는 단어에서 틀린 성조가 나올 수 있습니다. 병음이 정확한지는 `TODO.md`의 6-3 항목에서 교정 품질과 함께 평가합니다. 수준 설정(`TODO.md`의 3번 항목)과의 관계, 특히 고급 수준에서 병음을 끌 수 있게 할지는 3번 작업을 진행할 때 결정합니다.

## 9. 켜기와 끄기는 전역 상태 파일로 관리하고, 스킬이 불러올 때 스크립트를 실행한다

- **결정**: `/chinese-proofread:toggle` 스킬은 `~/.claude/chinese-proofread/state.json`에 `enabled` 값을 기록하고, `detect_chinese.py`는 판별을 시작하기 전에 이 값을 읽습니다. 스킬은 `SKILL.md` 본문의 ``!`python3 ${CLAUDE_PLUGIN_ROOT}/scripts/toggle.py $ARGUMENTS` ``로 스크립트를 실행하므로, 모델은 실행 결과를 전달하기만 합니다. 환경 변수 `CHINESE_PROOFREAD_ENABLED=0`을 설정하면 상태 파일과 관계없이 기능이 꺼집니다.
- **이유**:
  - 상태 파일은 훅이 입력마다 새로 읽으므로, Claude Code를 다시 시작하지 않아도 다음 입력부터 바로 반영됩니다.
  - 기능을 켜고 끄는 기준은 대부분 사용자가 중국어를 학습하는 중인지 여부이고, 이 기준은 프로젝트마다 달라지지 않습니다. 그래서 상태를 전역으로 하나만 둡니다. 특정 프로젝트에서만 항상 끄는 경우는 그 프로젝트의 설정에 환경 변수를 넣어 처리합니다.
  - 스킬을 불러올 때 스크립트를 실행하면 모델이 도구를 호출하지 않으므로, 권한 확인이 뜨지 않고 토큰도 적게 소비합니다.
  - 상태 파일이 없거나 손상되었으면 켜진 것으로 간주합니다. 설치 직후에도 별도의 설정 없이 동작해야 하기 때문입니다.
- **대안**:
  - 환경 변수만으로 켜고 끄는 방법이 있습니다. 하지만 값을 바꿀 때마다 Claude Code를 다시 시작해야 하므로, 잠시 끄는 용도로는 불편합니다.
  - 상태를 프로젝트마다 따로 저장하는 방법이 있습니다. 하지만 이 방법을 쓰면 프로젝트를 옮겨 다닐 때 어디에서 켜져 있고 어디에서 꺼져 있는지 알기 어렵습니다.
  - 모델이 Bash나 Write 도구로 상태 파일을 쓰게 하는 방법이 있습니다. 하지만 이 방법은 권한 확인이 뜰 수 있고, 모델이 지시와 다르게 파일을 쓸 가능성도 있습니다.
  - 인자 없이 상태를 반전하기만 하는 방법이 있습니다. 하지만 사용자가 현재 상태를 모르는 채로 명령을 실행하게 되므로, `on`, `off`, `status` 인자도 함께 받습니다.
- **트레이드오프**:
  - 스킬이 `!` 명령을 실행하려면 프런트매터에 `allowed-tools: Bash(python3:*)`가 있어야 합니다. 이 동작은 Claude Code 2.1.312에서 확인했으므로, 이후 버전에서 스킬의 동작 방식이 바뀌면 다시 확인해야 합니다.
  - 상태 파일의 경로는 `toggle.py`와 `detect_chinese.py`에 각각 적혀 있으므로, 경로를 바꿀 때는 두 파일을 함께 고쳐야 합니다.
  - 스크립트의 결과를 사용자에게 전달하는 과정에서는 여전히 모델이 응답을 생성하므로, 토큰이 조금 소비됩니다.

## 10. 중국어 대신 쓴 단어를 알려 주고, 영문자가 섞인 짧은 입력도 판별한다

- **결정**:
  - 사용자가 중국어로 모르는 단어를 영어나 한국어로 대신 쓰면(예: `跑local server.`), 스킬은 그 단어를 중국어권 개발자가 쓰는 표현으로 바꾸어 `修正`에 반영하고, 설명에서 그 단어를 중국어로 어떻게 말하는지 병음과 함께 알려 줍니다. 그다음에 원래 요청을 수행합니다.
  - 중국어 문장 안에 쓴 영어나 한국어 단어는 세 종류로 나눕니다(2026-10-30에 수정).
    1. 코드, 명령어, 파일 경로, 식별자, 약어(`API`, `JSON`, `PR`), 제품이나 서비스의 이름, 브랜치 이름처럼 원래 영어로 쓰는 부분은 바꾸지 않고 설명도 덧붙이지 않습니다.
    2. 그 밖의 단어는 중국어권 개발자가 영어로도 흔히 쓰는 단어(`fix`, `commit`, `edge case`)라도 중국어로 바꾸어 `修正`에 반영하고 설명에서 알려 줍니다. 어느 종류인지 애매한 단어도 여기에 넣습니다.
    3. 중국어 문장에서도 영어로 굳어진 단어는 바꾸지 않고 설명도 덧붙이지 않습니다. 이 종류는 `SKILL.md`에 적은 목록에 있는 단어로만 한정하며, 지금은 `bug` 하나만 넣었습니다.
  - 훅은 영문자가 섞여 있고 한글이 없는 입력에 `CHINESE_PROOFREAD_MIN_HANZI_MIXED`(기본값 1)를 최소 한자 수로 적용합니다. 2026-10-30에 14번 항목에 따라, 한글이 섞인 입력에도 이 값을 적용하도록 넓혔습니다.
  - 알려 줄 단어가 있으면 다른 고칠 부분이 없어도 `原文`과 `修正` 형식으로 출력합니다. `✅` 줄 아래에는 설명을 덧붙이지 않습니다.
- **이유**:
  - 중국어를 연습하는 사용자는 모르는 단어 때문에 중국어 입력을 포기하기 쉽습니다. 모르는 단어만 영어로 쓰고 나머지를 중국어로 쓰게 하면 연습을 계속할 수 있고, 그 단어가 바로 학습할 거리가 됩니다.
  - 기존 판별 규칙은 한자를 4자 이상 요구하므로, `跑local server.`처럼 한자가 1자뿐인 입력은 감지하지 못했습니다. 모르는 단어를 영어로 대신 쓴 문장은 한자가 적은 경우가 많으므로 이 규칙만으로는 새 기능이 동작하지 않습니다.
  - 최소 한자 수를 둔 이유는 한국어 문장에 섞인 한자 때문에 오판하는 경우를 막기 위해서였습니다(2번 항목). 한글이 없는 입력에는 이 위험이 없으므로 기준을 낮춥니다.
  - 영문자가 없는 입력에는 기존 기준을 유지합니다. 그렇지 않으면 `好的`, `谢谢`처럼 짧은 대답을 입력할 때마다 `✅` 줄이 출력됩니다.
- **대안**:
  - 모든 입력에서 최소 한자 수를 1로 낮추는 방법이 있습니다. 하지만 이 방법을 쓰면 위에서 설명한 것처럼 짧은 대답에도 교정 결과가 출력되고, 한국어 문장에 섞인 한자도 오판하기 쉬워집니다.
  - 한글이 섞인 입력에서도 기준을 낮추어 `跑로컬 서버`까지 판별하는 방법이 있습니다. 하지만 한자와 한글의 비율로는 한국어 대신 쓴 중국어 문장과 한자가 섞인 한국어 문장을 구분할 수 없으므로 선택하지 않았습니다. 이후 14번 항목에서 한자가 섞인 한국어 문장도 교정하기로 하면서, 두 경우를 구분할 필요가 없어졌으므로 이 방법을 택했습니다.
  - 영어 단어를 중국어 표현으로 모두 바꾸는 방법이 있습니다. 하지만 `改bug`처럼 영어로 굳어진 표현까지 바꾸면 오히려 부자연스러운 문장을 가르치게 되므로, 3번 종류의 목록을 따로 둡니다.
  - 처음에는 "사용자가 중국어로 어떻게 말하는지 모르는 단어"만 바꾸고, 중국어 표현과 영어 표현을 모두 흔히 쓰는 단어는 영어를 유지하면서 중국어 표현을 `✅` 줄 아래에 알려 주었습니다. 하지만 사용자가 그 단어를 알고 있었는지는 모델이 알 수 없으므로 판단이 흔들렸습니다. `TODO.md`의 6-3에서 실행한 평가에서 Sonnet은 `fix`를 `修`로 바꾸기도 하고 그대로 두기도 했으며, 두 모델 모두 `edge case`, `output`, `installation`에서 출력 형식이 갈렸습니다(`docs/eval-6-3-skill-review.md`의 3번 항목). 그래서 사용자의 의도가 아니라 단어 자체를 보고 판단하는 지금의 기준으로 바꾸었습니다.
  - "중국어권 개발자가 이 문장에서 이 단어를 영어로 쓰는가"를 기준으로 삼고, 애매하면 영어를 그대로 두는 방법도 검토했습니다. 이 방법은 사용자가 쓴 표현을 존중하지만, 판단을 여전히 모델에 맡기므로 일관성 문제가 남습니다. 또한 이 플러그인의 목적은 중국어 학습이므로, 애매한 단어는 중국어 표현을 알려 주는 쪽이 목적에 더 맞습니다.
- **트레이드오프**:
  - 영어 요청에 한자가 한 글자라도 들어 있으면 훅이 지시문을 추가하므로 토큰이 조금 소비됩니다. 교정할 대상이 있는지는 4번 항목의 원칙에 따라 스킬이 판단합니다.
    - 2026-10-29에 `TODO.md`의 6-2에서 측정했을 때, 한자가 섞인 영어 요청 14개에 훅이 모두 반응했습니다. `MIN_HANZI_MIXED`를 2로 올리면 이 중 2개만 반응하지 않게 되고, 감지해야 하는 `跑local server.`, `deploy到staging`, `merge到main`을 놓치게 됩니다. 따라서 기본값 1을 유지했습니다.
  - 모르는 단어를 한국어로 대신 쓴 짧은 문장은 여전히 감지하지 못합니다. 이 한계는 14번 항목에서 해결했습니다.
  - `commit`이나 `deploy`처럼 중국어권 개발자가 실제로는 영어로 더 자주 쓰는 단어도 중국어로 바뀌므로, `修正` 문장이 실제 개발자의 문장보다 교과서에 가까워질 수 있습니다. 학습을 우선하여 이 차이를 받아들였습니다.
  - 1번 종류(원래 영어로 쓰는 부분)에 속하는지는 여전히 모델이 판단합니다. 다만 약어, 이름, 코드처럼 겉모양으로 구분할 수 있는 경우가 대부분이므로, 이전 기준보다 판단이 덜 흔들릴 것으로 예상합니다. 이 판단은 `TODO.md`의 6-3 항목에서 교정 품질과 함께 평가합니다.

## 11. 판별 로직은 `unittest`로 테스트하고, GitHub Actions가 Python 3.9와 3.14에서 실행한다

- **결정**:
  - 판별 조건을 `is_chinese()` 함수로 분리하고, 저장소 루트의 `tests/test_detect_chinese.py`에서 표준 라이브러리 `unittest`로 테스트합니다.
  - 테스트는 두 종류로 나눕니다. `is_chinese()`를 직접 호출하여 판별 규칙을 검사하는 테스트와, `subprocess`로 훅 스크립트를 실제로 실행하여 입력 처리와 출력과 종료 코드를 검사하는 테스트입니다.
  - 훅을 실행하는 테스트에서는 `HOME`을 임시 폴더로 바꾸고, `CHINESE_PROOFREAD_`로 시작하는 환경 변수를 모두 지웁니다.
  - 알려진 한계는 올바른 기대값을 검사하는 테스트로 작성하고 `@unittest.expectedFailure`를 붙입니다.
  - GitHub Actions는 `main` 브랜치에 push할 때와 pull request를 열 때 Python 3.9와 3.14에서 테스트를 실행합니다.
    - 2026-10-30에 저장소를 공개하고 처음 push했을 때, 두 버전의 작업이 모두 성공했습니다.
- **이유**:
  - 플러그인 사용자는 외부 패키지 없이 훅을 실행하므로, 테스트도 외부 패키지 없이 실행할 수 있어야 개발 환경을 따로 준비하지 않아도 됩니다.
  - 테스트를 플러그인 폴더 밖에 두어야 사용자가 플러그인을 설치할 때 테스트 파일을 받지 않습니다.
  - 판별 규칙만 검사해서는 JSON이 아닌 입력이나 잘못된 환경 변수 값 때문에 훅이 오류로 종료되는 경우를 발견할 수 없습니다. 이런 경우는 스크립트를 실제로 실행해야 확인할 수 있습니다.
  - `HOME`을 바꾸지 않으면 테스트가 실제 `~/.claude/chinese-proofread/state.json`을 읽으므로, 개발자가 교정 기능을 꺼 두었을 때 테스트가 실패합니다. 개발자가 설정해 둔 환경 변수도 같은 이유로 지웁니다.
  - `expectedFailure`를 쓰면 지금은 실패가 정상으로 처리되고, 나중에 판별 규칙이 그 한계를 해결하면 예상과 달리 성공한 테스트가 실패로 보고됩니다. 따라서 한계가 해결된 시점을 놓치지 않습니다.
  - 훅은 사용자 컴퓨터에 설치된 `python3`로 실행됩니다. macOS에 기본으로 설치된 `python3`가 3.9이므로 3.9를 지원할 가장 낮은 버전으로 정했고, 새 버전에서 없어진 기능을 쓰는지도 확인하기 위해 최신 버전인 3.14도 함께 검사합니다.
- **대안**:
  - `pytest`를 쓰는 방법이 있습니다. 테스트 코드는 더 짧아지지만, 개발자와 GitHub Actions가 패키지를 설치해야 하므로 선택하지 않았습니다.
  - 알려진 한계를 지금의 잘못된 결과를 기대값으로 삼아 테스트하는 방법이 있습니다. 하지만 이 방법을 쓰면 잘못된 동작이 의도한 동작처럼 보이고, 한계를 해결했을 때 테스트를 고쳐야 한다는 사실도 드러나지 않습니다.
  - 테스트를 개발자가 직접 실행하게만 하는 방법이 있습니다. 하지만 테스트를 잊고 커밋하는 경우를 막을 수 없고, 3.9처럼 개발 환경에 없는 버전에서는 테스트를 실행하기 어렵습니다.
- **트레이드오프**:
  - Python 3.10~3.13은 검사하지 않습니다. 양 끝 버전에서 통과하면 그 사이의 버전에서도 대부분 동작한다고 보았습니다.
  - Python 3.9는 공식 지원이 끝난 버전이므로, GitHub Actions에서 이 버전을 더 이상 제공하지 않게 되면 가장 낮은 버전을 다시 정해야 합니다.
  - Windows와 macOS에서는 테스트를 실행하지 않습니다.

## 12. 판별 설정값은 전체 오탐률이 아니라 범주별 조건으로 고른다

- **결정**:
  - `TODO.md`의 6-2에서 판별 설정값을 고를 때, 먼저 범주별 조건을 만족하는 설정만 남깁니다. 중국어 문장(`zh_pure`, `zh_traditional`, `zh_with_code`)과 영어로 대신 쓴 단어가 들어 있는 중국어 문장(`zh_english_substitute`)은 모두 감지해야 하고, 한국어 요청(`ko_pure`), 영어나 코드만 있는 입력(`en_or_code`), 짧은 중국어 대답(`zh_short_reply`)에는 하나도 반응하지 않아야 합니다.

- **이유**:
  - 처음에는 "오탐률이 10% 이하인 설정 중에서 재현율이 가장 높은 설정"을 기준으로 정했습니다. 그런데 이 기준으로 고른 설정(4 / 3 / 0.6)은 설계 결정 10번에서 감지하려고 했던 `跑local server.` 같은 입력을 놓쳤습니다.
  - 오탐률은 true 문장과 false 문장의 비율에는 영향을 받지 않지만, false 문장들 사이의 구성에는 영향을 받습니다. 이 데이터셋에는 판별하기 어려운 false 문장을 일부러 많이 넣었기 때문에, 전체 오탐률이 실제 사용 환경보다 훨씬 높게 나옵니다. 따라서 전체 오탐률에 한도를 두면 실제로는 드문 오탐을 없애기 위해 핵심 기능을 포기하는 설정이 뽑힙니다.
  - 오탐의 비용과 놓쳤을 때의 비용은 범주마다 다릅니다. 영어 요청에 한자가 섞인 문장에서 오탐이 생기면 지시문만큼 토큰이 소비되고 스킬은 교정을 건너뜁니다. 반면 중국어 문장을 놓치면 교정 기능이 동작하지 않습니다. 가장 많이 들어오는 한국어 요청에서 오탐이 생기면 매번 토큰이 소비되므로, 이 범주에서는 오탐을 허용하지 않습니다.
- **대안**:
  - 처음 기준을 그대로 적용하는 방법이 있습니다. 하지만 이 방법을 쓰면 설계 결정 10번의 기능을 포기해야 합니다.
  - 범주 조건을 만족하는 설정 중에서 재현율이 가장 높은 설정을 고르는 방법도 검토했습니다. 하지만 이 방법으로 고른 설정(3 / 1 / 0.3)은 조정용 세트에서 재현율을 4개 문장만큼 올리는 대신 오탐을 6개 늘렸습니다. 이처럼 재현율과 오탐을 맞바꾸는 판단은 하나의 숫자로 정하기 어렵다고 보았습니다.
  - 실제로 입력했던 프롬프트를 데이터셋에 넣어서 문장 구성을 실제 사용 환경에 맞추는 방법이 있습니다. 이 방법을 쓰면 전체 오탐률을 그대로 기준으로 쓸 수 있지만, 프롬프트를 모으고 검토하는 데 시간이 더 걸리므로 이번에는 선택하지 않았습니다.
- **트레이드오프**:
  - 기준을 결과를 본 뒤에 바꾸었으므로, 결과에 맞춰 기준을 정했다는 의심을 받을 수 있습니다. 이 위험을 줄이기 위해 처음 기준과 그 기준으로 고른 설정, 기준을 바꾼 이유를 `docs/eval-results.md`와 이 항목에 함께 남겼습니다. 바꾼 기준에서는 결과적으로 기본값을 유지했습니다.
  - 범주별 조건에 어느 범주를 넣을지는 사람이 판단합니다. 범주를 다르게 정하면 고르는 설정도 달라질 수 있습니다.
  - 재현율과 오탐을 맞바꾸는 설정 중에서 무엇을 고를지는 수치만으로 정해지지 않으므로, `TODO.md`의 9-2와 9-5에서 다시 판단해야 합니다.

## 14. 한국어나 영어 문장에 섞어 쓴 중국어 단어도 교정한다

- **결정**:
  - `设置 画面에 暗黑 模式 추가해 줘`나 `write a 测验 for average`처럼 사용자가 한국어나 영어 문장 안에 직접 섞어 쓴 중국어 단어도 교정합니다. 이 기능은 기본으로 켜 둡니다.
  - 훅은 영문자나 한글이 섞인 입력이면 한자가 `CHINESE_PROOFREAD_MIN_HANZI_MIXED`(기본값 1)자만 있어도 반응하고, `CHINESE_PROOFREAD_HANZI_RATIO`의 기본값은 0으로 낮춥니다. 한자만으로 쓴 입력은 지금처럼 `CHINESE_PROOFREAD_MIN_HANZI`(기본값 4)를 적용하므로, `好的` 같은 짧은 대답에는 반응하지 않습니다.
  - 스킬은 틀린 단어만 `- 原 → 正(병음): 설명` 형식으로 알려 주고, 고칠 단어가 없으면 아무것도 출력하지 않습니다(16번 항목에서 `✅` 줄을 출력하도록 바꾸었습니다). 따옴표나 백틱으로 감싼 중국어, 번역하거나 뜻을 설명해 달라고 한 중국어, 파일 안의 중국어는 인용한 것으로 보고 교정하지 않습니다.
  - 사용자가 직접 쓴 한자는 한국어 한자어처럼 보여도 중국어로 보고 교정합니다(예: `中國語` → `中文`). 간체자와 번체자는 기존 규칙대로 사용자가 쓴 글자 형태를 유지합니다.
- **이유**:
  - 사용자가 직접 고른 중국어 단어는 문장이 아니어도 학습할 거리입니다. `TODO.md`의 6-2에서 데이터셋을 검토하면서 `word` 문장도 교정하는 편이 좋다고 판단했습니다.
  - 6-2의 측정에서 단어 포함 기준의 재현율과 오탐률은 한자 수와 비율만으로는 함께 좋아지지 않았습니다(조정용 세트에서 0.946 / 0.414와 0.589 / 0.034). 따라서 훅은 넓게 반응하고, 직접 쓴 단어인지는 문맥을 보는 모델이 판단하도록 4번 항목의 원칙을 넓혔습니다.
  - 2026-10-30에 `try/9-5` 브랜치에서 시험용 규칙으로 케이스 9개를 실행했습니다. 틀린 단어 4개(`例外`, `测验`, `设置画面`, `中國語`)는 Sonnet과 Opus 모두 12회 중 12회 교정했습니다. 인용하거나 붙여 넣은 중국어가 있는 케이스 3개(9회)와 맞는 단어만 섞어 쓴 케이스 2개(6회)에서는 두 모델 모두 한 번도 교정 블록을 출력하지 않았습니다. 자세한 결과는 `docs/eval-results.md`의 "9-5 시험"에 기록했습니다.
  - 문장 전체를 `原文`과 `修正`으로 다시 쓰면 한국어나 영어 문장이 그대로 반복되어 읽기 어려우므로, 고친 단어만 한 줄에 하나씩 씁니다. 맞는 단어마다 `✅` 줄을 출력하면 중국어 단어를 섞을 때마다 의미 없는 줄이 붙으므로, 고칠 단어가 없으면 아무것도 출력하지 않습니다.
- **대안**:
  - 이 기능을 설정으로 켜야 동작하는 선택 사항으로 두는 방법을 검토했습니다. 하지만 이 플러그인의 사용자는 중국어 학습자이므로 기본으로 켜 두는 편이 목적에 맞고, 설정을 하나 더 만들지 않아도 아래 방법으로 끌 수 있으므로 선택하지 않았습니다.

  - 한국어 한자어를 건너뛰는 규칙을 두는 방법도 있습니다. 하지만 `部分`처럼 한국어 한자어와 중국어 단어의 모양이 같은 경우가 있어서 모델이 일관되게 지키기 어렵고, 중국어 학습자가 한국어 문장에 한자를 썼다면 중국어를 시도했을 가능성이 높으므로 선택하지 않았습니다.
- **트레이드오프**:
  - 한자가 한 글자라도 있는 한국어와 영어 요청에 훅이 반응하므로, 교정할 대상이 없어도 지시문만큼 토큰이 소비됩니다.
  - 중국어를 공부하지 않는 사용자가 한국어 한자어를 쓰면 필요 없는 교정을 받습니다. README에 `CHINESE_PROOFREAD_HANZI_RATIO`로 줄이는 방법을 안내했습니다.
  - 훅의 지시문에는 단어의 출력 규칙을 넣지 않고 `SKILL.md`에만 둡니다. 지시문에 "고칠 단어가 없으면 건너뛴다"는 조건을 넣었을 때는 Opus가 자연스러운 중국어 문장에서도 교정을 건너뛰었고(114회 중 3회), "중국어 문장에는 항상 결과를 쓴다"고 명시했을 때는 Sonnet이 맞는 단어에도 `慢 → 慢` 같은 블록을 출력했습니다(5회 중 4회). 출력 규칙을 빼자 두 문제가 모두 나타나지 않았습니다(각각 15회와 5회). 다만 최종 지시문으로는 문제가 나온 케이스만 실행했으므로, 전체 케이스의 결과는 다음 기준 점수에서 확인해야 합니다.
  - 직접 쓴 단어인지 인용한 중국어인지는 모델이 판단하므로 틀릴 수 있습니다. 시험에서 Sonnet은 첫 실행에서 `中國語` 케이스의 3회 중 2회 스킬을 불러오지 않았고, 훅의 지시문에 한국어 한자어처럼 보이는 단어도 포함한다고 덧붙인 뒤에는 3회 모두 교정했습니다.

## 15. 교정 블록의 설명 언어와 대화 응답 언어를 따로 정한다

> 설정과 언어 구분은 유지합니다. 다만 19번 항목에 따라 블록을 출력할 때가 아니라, 사용자가 쓴 중국어가 있다고 메인 모델이 판단할 때 대화 응답 언어를 적용합니다.

- **결정**:
  - Claude가 쓰는 텍스트를 교정 블록, 대화 응답, 작업 결과물로 나눕니다. 대화 응답은 교정 블록 밖에서 사용자에게 하는 말이며, 작업 중의 진행 상황, 되묻는 질문, 결과 요약을 포함합니다.
  - 교정 블록의 설명과 `✅` 줄은 `CHINESE_PROOFREAD_LANG`을, 대화 응답은 새 설정 `CHINESE_PROOFREAD_CHAT_LANG`을 따릅니다. `CHINESE_PROOFREAD_CHAT_LANG`을 지정하지 않으면 `CHINESE_PROOFREAD_LANG`과 같은 언어를, `prompt`로 지정하면 요청을 쓴 언어를, 그 밖의 값이면 지정한 언어를 씁니다.
  - 대화 응답의 언어는 훅의 `additionalContext`로 전달하고, 교정 블록을 출력할 때만 적용합니다. 작업 결과물(코드, 코드 주석, 커밋 메시지, 파일 내용)에는 적용하지 않고, 요청 내용과 저장소의 관례를 따르게 합니다.
  - `✅` 줄의 문구는 `자연스럽습니다.`로 고정하고, 설명 언어가 한국어가 아니면 그 언어로 옮긴 한 문장으로 씁니다.
  - 작업 내용은 [#2](https://github.com/robinyoon-dev/chinese-proofread/issues/2)에 기록했습니다.
- **이유**:
  - 교정 블록의 설명은 학습에 쓰이므로 사용자가 잘 아는 언어로 나와야 합니다. 반면 대화 응답에 원하는 언어는 사용자마다 다릅니다. 중국어로 요청했으니 중국어로 답해도 된다는 사용자도 있고, 작업 결과를 정확히 이해하려고 한국어 답변을 원하는 사용자도 있습니다.
  - #1에서 교정 블록을 작업 전에 쓰게 한 `try/11-gate`의 시범 실행에서는 설명 언어가 31회 중 30회 한국어였지만, 대화 응답은 31회 중 15회가 중국어였습니다. 교정 블록이 최종 답변의 맨 앞에 있을 때는 한국어 블록이 대화 응답의 언어까지 함께 정했던 것으로 보이며, 블록의 위치가 바뀌면 이 효과가 사라졌습니다. 따라서 대화 응답의 언어를 블록과 관계없이 따로 지시해야 했습니다.
  - 기본값을 설명 언어와 같게 둔 이유는, 대화 응답에 무엇을 지웠는지나 테스트를 실행하지 않았는지처럼 잘못 읽으면 곤란한 내용이 들어가기 때문입니다. 또한 기존의 README와 평가 결과가 한국어 답변을 기준으로 작성되어 있으므로, 기본 동작을 바꾸지 않으면 그대로 쓸 수 있습니다.
  - 훅의 지시문은 프롬프트마다 전달되므로, 스킬 본문에 쓰는 것보다 잘 지켜질 것으로 예상했습니다. 설명 언어도 이미 같은 방식으로 전달하고 있습니다.
  - 교정을 건너뛸 때는 플러그인이 답변에 드러나지 않아야 하므로 대화 응답의 언어도 지정하지 않습니다. 이 조건이 없으면 `translate "请稍后再试" to English`처럼 인용한 중국어만 있는 영어 요청에도 한국어로 답하게 됩니다.
- **대안**:
  - 환경 변수 이름으로 `CHINESE_PROOFREAD_REPLY_LANG`을 검토했습니다. 하지만 "reply"는 작업에 대한 답 전체로 읽혀서 코드나 파일 같은 작업 결과물까지 포함하는 것처럼 보이므로, 사용자와 주고받는 말이라는 뜻이 드러나는 `CHAT_LANG`을 골랐습니다.
  - 기존 `CHINESE_PROOFREAD_LANG`의 이름을 `CHINESE_PROOFREAD_EXPLAIN_LANG`처럼 바꾸는 방법도 검토했습니다. 하지만 README, 훅, 평가를 함께 고쳐야 하므로 이름은 그대로 두고, README의 설정 표에서 교정 블록의 설명 언어라는 점을 분명히 적었습니다.
- **트레이드오프**:
  - 대화 응답의 언어를 판정하는 채점자(`chat-korean`)는 정규식으로 판정하므로, 백틱이나 코드 블록 없이 인용한 중국어 문장은 대화 응답으로 잘못 셀 수 있습니다. 처음에는 한국어 문장이 있는지만 확인해서, 한국어 진행 문장 하나 뒤에 중국어로 답한 실행을 놓쳤습니다. 지금은 코드 블록 밖에 중국어 문장이 없는지도 확인합니다.
  - 평가는 기본값만 측정합니다. `claude plugin eval`은 셸에서 지정한 환경 변수를 자식 실행에 전달하지 않기 때문입니다. `prompt`나 언어 이름을 지정한 동작은 단위 테스트로 지시문의 내용을 확인했고, `claude -p --plugin-dir`로 값마다 1회씩 실행하여 실제 응답도 확인했습니다. 이 확인은 동작을 살펴본 것이며 비율을 측정한 것은 아닙니다. 결과는 [#2의 마지막 댓글](https://github.com/robinyoon-dev/chinese-proofread/issues/2)에 기록했습니다.
- **결과**:
  - `feat/reply-lang` 브랜치에서 Sonnet으로 케이스 38개를 1회씩 실행했을 때, 설명 언어와 대화 응답 언어 모두 33회 중 33회 한국어였습니다. 9-5 시험의 전체 실행(3회)에 같은 채점자를 적용한 결과는 각각 98/98과 94/98이었습니다.
  - `none-quoted-translation`의 1회에서는 교정을 건너뛴 사실을 언급하고 영어 요청에 한국어로 답했습니다. `try/11-gate`에 합친 뒤의 3회 평가에서는 이 케이스가 3회 모두 통과했습니다. 자세한 결과는 `docs/eval-results.md`의 "Issue #2: 대화 응답 언어 설정"에 기록했습니다.
  - `try/11-gate`에 합친 뒤 Sonnet으로 케이스마다 3회씩 실행했을 때, 교정 블록이 있는 84회 중 설명 언어는 84회, 대화 응답 언어는 83회 지켜졌습니다. 같은 게이트에서 #2를 적용하기 전에는 대화 응답이 31회 중 15회 중국어였습니다. 자세한 결과는 `docs/eval-results.md`의 "#1과 #2를 함께 측정한 3회 평가"에 기록했습니다.

## 16. 맞는 단어만 섞어 쓴 요청에도 `✅` 줄을 출력한다

> `✅` 줄의 규칙은 유지합니다. 게이트에 관한 이유는 19번 항목에서 게이트를 지웠으므로 더 이상 해당되지 않습니다. 트레이드오프에 적은 영어 요청의 답변 언어는 이제 메인 모델이 정하므로, 영어로 답할 수도 있습니다.

- **결정**: 사용자가 한국어나 영어 문장에 직접 섞어 쓴 중국어 단어가 모두 맞고 중국어 문장이 없으면, 자연스러운 문장과 같이 `✅` 줄 한 줄만 출력합니다. 14번 항목에서 아무것도 출력하지 않기로 한 결정을 바꾼 것입니다. 인용하거나 붙여 넣은 중국어만 있는 요청은 지금처럼 교정 블록을 출력하지 않습니다.
- **이유**:
  - 중국어를 배우는 사용자에게는 자신이 고른 단어가 맞다는 확인도 학습에 도움이 됩니다.
  - 판단 기준이 "사용자가 직접 쓴 중국어가 있으면 항상 결과를 보여 준다"로 단순해집니다. 문장과 단어를 구분할 필요가 없어집니다.
  - #1의 게이트는 블록이 없는 도구 호출을 거부합니다. 지금까지는 맞는 단어만 쓴 요청도 한 번 거부되었고, 거부 메시지를 강화한 평가에서는 6회 모두 `✅` 줄을 출력했습니다. 이 동작을 실패로 보고 메시지의 예외를 늘리면, 교정 블록 누락이 되살아날 위험이 있습니다.
- **대안**: 14번 항목의 규칙을 유지하고, 거부 메시지의 예외에 고칠 단어가 없는 경우를 넣는 방법을 검토했습니다. 답변은 더 깔끔하지만, 예외를 넓히면 모델이 고칠 것이 없다고 판단하고 다시 호출할 길이 생기므로 선택하지 않았습니다.
- **트레이드오프**:
  - 맞는 단어를 섞어 쓸 때마다 답변 맨 앞에 같은 줄이 붙습니다. 이 `✅`는 단어가 맞다는 뜻일 뿐이며, 한국어나 영어 부분을 점검했다는 뜻은 아닙니다.
  - 교정 블록을 출력하면 15번 항목의 대화 응답 언어가 적용되므로, `this API is too 慢`처럼 영어로 쓴 요청에도 기본값에서는 한국어로 답합니다.

## 17. 교정 결과를 작업 전에 보여 주고, 이 순서를 훅으로 강제한다

> 이 결정은 19번 항목으로 바뀌었습니다. 게이트는 대화형 세션에서 동작하지 않았습니다. 아래의 수치는 비대화형 평가의 결과입니다. 아래 내용은 당시의 판단 근거로 남겨 둡니다.

- **결정**:
  - 순서를 "요청 수행 → 최종 답변의 맨 앞에 교정 결과 출력"에서 "교정 결과 출력 → 요청 수행"으로 바꿉니다. 13번 항목의 결정을 바꾼 것입니다. 교정 결과는 최종 답변에 다시 쓰지 않습니다.
  - `detect_chinese.py`는 중국어를 감지하면 프롬프트 id를 pending 파일에 남깁니다.
  - `require_block_first.py`(`PreToolUse`)는 교정 블록을 쓰지 않은 도구 호출을 프롬프트마다 두 번까지 거부하고, 그 뒤의 호출은 통과시킵니다. 다음 메시지에서 도구를 호출하지 말고 블록만 쓰라고 요청합니다.
  - `continue_after_block.py`(`Stop`)는 블록만 쓴 답변이나 거부된 뒤의 답변으로 턴이 끝나려 하면, 턴을 한 번 이어 가게 합니다.
- **이유**:
  - 13번 항목의 트레이드오프대로, 대화형 세션에서는 작업이 끝날 때까지 교정 결과를 볼 수 없었습니다. 사용자는 작업 결과보다 교정 결과를 먼저 보고 싶어 합니다([#1](https://github.com/robinyoon-dev/chinese-proofread/issues/1)).
  - `SKILL.md`의 문구만 바꾼 `try/11`에서는 교정 블록이 있어야 하는 33회 중 18회에서 블록이 나오지 않았습니다. Sonnet이 고칠 부분을 생각 블록에만 적고 도구를 호출했기 때문입니다. 문구로는 이 동작을 막지 못했으므로, 도구를 호출하는 지점을 훅이 직접 막기로 했습니다.
  - Sonnet은 도구 호출이 없는 답변에서는 블록을 잘 쓰므로, 거부 메시지에서 블록만 쓴 답변을 요청합니다. 이 답변으로 턴이 끝나지 않도록 `Stop` 훅이 필요합니다.
  - 한 번만 거부했을 때는 `fix`와 `word` 63회 중 블록이 없는 실행이 7회에서 15회였습니다. Sonnet이 교정을 마쳤다고 생각 블록에 적고 같은 호출을 다시 했기 때문입니다. 두 번 거부하고 거부 메시지를 강화한 뒤에는 0회였습니다.
  - Opus는 두 번 거부된 뒤 작업을 멈추기도 했으므로(114회 중 2회), 거부된 뒤에 끝나려는 턴도 `Stop` 훅이 이어 가게 했습니다.
- **대안**:
  - 작업 전과 최종 답변에 블록을 두 번 쓰는 방법은 13번 항목에서 검토한 대로 대화형 세션에서 같은 블록이 두 번 보이므로 선택하지 않았습니다.
  - 훅의 지시문을 강화하는 방법은 모델이 문구를 따른다는 전제에 의존합니다. `try/11`에서 문구를 바꾼 방법이 효과가 없었으므로 시도하지 않았습니다.
  - 블록이 나올 때까지 계속 거부하는 방법을 시험했지만, Sonnet이 훅이 잘못 막고 있다고 쓰고 다른 도구로 우회하려 했으므로 횟수를 두 번으로 제한했습니다.
  - 지금 방식을 유지하는 방법도 있었습니다. 하지만 게이트로 작업 전 출력이 가능하다는 사실을 확인했으므로 선택하지 않았습니다.
- **트레이드오프**:
  - 거부될 때마다 왕복이 늘어납니다. Opus는 `fix`와 `word` 63회 중 29회에서 두 번째 거부까지 갔습니다.
  - 최종 답변에는 블록이 없으므로, `claude -p`처럼 최종 답변만 보여 주는 환경에서는 교정 결과를 볼 수 없습니다. 13번 항목이 얻었던 장점을 포기한 것입니다.
  - 훅이 transcript 형식에 의존합니다. 블록을 썼는지 확인하려면 훅이 자신의 `tool_use_id`가 transcript에 기록될 때까지 기다려야 하며, 시간 안에 기록되지 않으면 호출을 통과시킵니다.
  - 횟수를 제한했으므로 블록 누락을 완전히 막지는 못합니다.
- **결과**:
  - 커밋 `754462c`의 전체 평가에서 `fix`와 `word` 63회 중 교정 블록을 쓴 실행은 Sonnet이 63회, Opus가 62회였습니다. 모든 텍스트 블록 기준의 형식 준수는 Sonnet 0.991(342/345), Opus 0.991(341/344)입니다. 자세한 결과는 `docs/eval-results.md`의 "#12 수정 뒤의 전체 평가"에 기록했습니다.

## 18. 교정 스킬을 불러온 세션에서만 도구 호출을 거부한다

> 이 결정은 19번 항목에서 게이트를 지우면서 더 이상 적용되지 않습니다. 아래 내용은 당시의 판단 근거로 남겨 둡니다.

- **결정**: 이 세션에서 `chinese-proofread:proofread` 스킬을 불러온 적이 없으면 게이트가 도구 호출을 거부하지 않습니다. 확인 범위는 현재 프롬프트가 아니라 세션 전체입니다.
- **이유**:
  - 판별 훅은 한자가 한 글자만 있어도 반응하므로, 코드나 데이터로 다루는 한자와 인용한 중국어에도 게이트가 걸립니다. 거부 메시지는 사용자가 쓴 중국어가 없으면 같은 호출을 다시 하라고 안내하지만, 게이트는 다시 한 호출도 거부했습니다. 그래서 모델은 교정 대상이 아니라고 맞게 판단하고도 두 번 거부되었고, 이를 훅의 고장으로 보고 답변에서 언급했습니다([#12](https://github.com/robinyoon-dev/chinese-proofread/issues/12)).
  - 평가 trace 494회를 집계했더니, 모델의 판단은 스킬 호출 여부로 이미 드러나 있었습니다. 도구를 쓴 `fix`, `word`, `ok`, `ask` 실행은 예외 없이 첫 호출 전에 스킬을 불러왔고, `none` 실행은 26회 중 1회만 불러왔습니다. 새로운 신호를 만들 필요가 없습니다.
  - 평가는 프롬프트가 하나뿐이지만, 실제 세션에서는 두 번째 중국어 프롬프트에서 스킬을 다시 부르지 않을 수 있습니다. 확인 범위를 현재 프롬프트로 좁히면 이런 프롬프트에서 게이트가 빠지므로, 세션 전체를 확인합니다.
- **대안**:
  - 처음 제안한 대로 `SKILL.md`에 예시만 넣는 방법은 부족했습니다. Opus는 이미 교정 대상이 아니라고 맞게 판단했는데도 거부되었기 때문입니다. 예시는 함께 넣었습니다.
  - `add 中 to the font test`의 기대 동작을 `✅` 줄 출력으로 바꾸는 방법은 `none-ko-pasted-error`처럼 인용한 중국어에서 같은 문제가 생기므로 해결이 되지 않습니다.
  - 따옴표나 백틱 안의 한자를 게이트에서 제외하는 방법은 코드로 처리할 수 있지만, `add 中`을 구분하지 못합니다.
  - 교정 대상이 없다는 신호를 모델이 보내게 하는 방법은 스킬 인자나 별도 스킬이 필요합니다. 또한 Sonnet이 교정을 건너뛸 길을 열어 주므로 선택하지 않았습니다.
- **트레이드오프**:
  - 모델이 스킬을 불러오지 않고 작업을 시작하면 게이트가 막지 못합니다. 지금까지의 평가와 수정 뒤의 전체 평가에서는 `fix`와 `word`에 이런 실행이 없었습니다.
  - 같은 세션에서 앞선 프롬프트가 스킬을 불러왔다면, 교정할 대상이 없는 요청은 이전처럼 거부됩니다. 평가가 프롬프트 하나로 실행되므로 이 경우는 측정하지 못했습니다.
- **결과**:
  - 전체 평가의 `none` 케이스에서 도구 호출이 거부된 실행은 두 모델 모두 9회 중 6회에서 0회로, 답변에 훅을 언급한 실행은 Sonnet 2회와 Opus 4회에서 0회로 줄었습니다. `fix`와 `word`의 교정 블록 누락은 늘지 않았습니다. 자세한 결과는 `docs/eval-results.md`의 "#12 수정 뒤의 전체 평가"에 기록했습니다.

## 19. 교정을 별도 프로세스에서 실행하고, 끝나는 대로 훅의 `systemMessage`로 표시한다

- **결정**:
  - `detect_chinese.py`는 중국어를 감지하면 `proofread_worker.py`를 분리된 프로세스로 실행하고 바로 끝납니다. 작업과 교정은 동시에 시작합니다.
  - `proofread_worker.py`는 `claude -p`로 교정하고, 결과를 세션별 폴더(`~/.claude/chinese-proofread/jobs/<세션 id>/`)에 저장합니다.
  - `show_result.py`는 `PostToolUse`, `PostToolUseFailure`, `Stop` 훅에서 끝난 결과를 `systemMessage`로 한 번만 표시합니다. `Stop`에서는 실행 중인 교정을 최대 20초 기다리고, 그래도 끝나지 않으면 다음 턴에 표시합니다.
  - 교정 모델은 Sonnet입니다. 교정 규칙은 `proofread` 스킬에서 `prompts/proofread.md`로 옮겼고, 스킬과 게이트와 `Stop` 재개 로직은 지웠습니다.
  - 메인 모델은 원문을 기준으로 작업합니다. 훅의 지시문은 교정하지 말라는 지시, 해석이 갈리면 먼저 확인하라는 지시, 답변 언어만 전달합니다.
  - 요구 사항을 "작업 전에 보여 주기"에서 "끝나는 대로 보여 주기"로 바꿉니다. 17번과 18번 항목을 대체하는 결정입니다.
  - 작업 내용은 [#18](https://github.com/robinyoon-dev/chinese-proofread/issues/18)에 기록했습니다.
- **이유**:
  - 대화형 세션에서는 `PreToolUse` 훅이 도는 동안 현재 응답이 transcript에 기록되지 않으므로, 게이트가 블록을 확인하지 못하고 호출을 통과시켰습니다. 대화형으로 실행한 5회 중 블록이 나온 것은 1회였습니다. [훅 문서](https://code.claude.com/docs/en/hooks)도 transcript가 비동기로 기록된다고 설명하므로, 게이트를 고쳐서 해결할 문제가 아닙니다.
  - 교정이 메인 모델 밖에서 실행되면, 모델이 블록을 건너뛰는 문제가 구조적으로 사라집니다.
  - `async` 훅의 `systemMessage`는 사용자에게 보이지 않으므로, 교정은 별도 프로세스로 실행하고 표시는 동기 훅이 맡습니다.
  - `PreToolUse`는 표시에 쓰지 않습니다. 이슈에서는 표시 훅으로 계획했지만, 시험해 보니 `PreToolUse`의 메시지는 도구가 끝난 뒤에야 보였습니다(15초 명령에서 17.6초). 게다가 권한 창에서 거부하거나 Esc를 누르면 메시지가 사라졌습니다. 즉 `PostToolUse`보다 빠르지 않고, 교정 결과를 잃을 위험만 있습니다.
  - `claude -p`에는 `--bare`를 쓰지 않습니다. `--bare`는 OAuth를 읽지 않으므로 구독 사용자에게서 실패합니다. 대신 `--tools ""`, `--setting-sources ""`, `--strict-mcp-config`로 격리합니다. 재귀 실행은 `--setting-sources ""`로 막히는 것을 확인했고, 환경 변수 `CHINESE_PROOFREAD_INTERNAL`을 두 번째 안전장치로 둡니다.
  - 모델의 출력은 교정 블록이나 `NONE`으로 시작해야 합니다. 그 밖의 출력은 모델이 프롬프트의 요청에 답한 것으로 보고 실패로 처리합니다.
  - 교정 모델을 Sonnet으로 정한 이유는 Haiku가 틀린 문장을 `✅`로 넘기는 경우가 있었기 때문입니다. 케이스 38개를 3회씩 실행했을 때 오류 검출은 Haiku 37/45, Sonnet 45/45였고, 지연도 Sonnet이 더 짧았습니다(중앙값 5.3초와 3.9초). 비용은 Sonnet이 약 10배이지만 1회에 $0.01 미만입니다.
  - 스킬을 지운 이유는 스킬이 남아 있으면 메인 모델도 교정해서 블록이 두 번 나올 수 있기 때문입니다.
- **대안**:
  - 게이트가 읽을 수 있는 기록으로 판단하도록 고치는 방법은, `PreToolUse`에서 현재 응답을 확인할 공식 경로가 없으므로 선택하지 않았습니다.
  - 첫 도구 호출을 transcript 확인 없이 한 번 거부하고 `Stop`에서 블록을 확인하는 방법을 [#18의 댓글](https://github.com/robinyoon-dev/chinese-proofread/issues/18)에서 검토했습니다. 작업 전 순서를 유지할 수 있지만, 재시도가 생기고 블록이 중복될 수 있으며 모델이 블록을 건너뛰는 문제가 남습니다.
  - 훅 안에서 교정이 끝날 때까지 기다리는 방법(english-buddy와 prompt-english-coach의 `gate` 모드)은 순서를 가장 확실히 보장하지만, 프롬프트마다 작업 시작이 늦어지므로 선택하지 않았습니다.
  - 첫 도구 호출에서 교정 결과를 기다리는 방법은 작업 시작이 몇 초 늦어지고 병렬 실행의 장점이 줄어듭니다.
  - 지시문의 문구는 여러 순서를 시험했습니다.
    - 언어 규칙을 조건으로 시작하면 도구 없는 짧은 답변이 중국어로 나왔습니다.
    - 언어 규칙을 맨 앞에 두면 그 유형은 나아졌지만, 긴 파일 작업 뒤의 답변이 중국어로 돌아갔고(`ok-add-comment` 3회 모두) `add 中`에도 한국어로 답했습니다.
    - 그래서 작업 지시, 예외, 언어 규칙의 순서로 두어 언어 규칙이 지시문의 끝에 오게 했습니다.
    - 언어 이름을 끝에서 한 번 더 말하는 문구는 `CHINESE_PROOFREAD_LANG=English`에서 효과가 없어 넣지 않았습니다.
  - "해석이 갈리면 먼저 확인"을 그대로 복원하자 Sonnet이 정보만 부족한 요청에도 되물었습니다(`fix-substitute-installation` 3회 모두). 그래서 정보가 부족할 뿐이면 합리적으로 정해서 진행하라고 범위를 좁혔습니다.
  - `설명:` 라벨을 설명 언어로 옮기라는 지시는 라벨을 안정적으로 바꾸지 못했고, `fix` 케이스 17회의 표본에서 형식 점수도 떨어졌으므로 되돌렸습니다.
- **트레이드오프**:
  - 교정 결과가 작업 전에 나온다고 보장하지 못합니다. 훅은 도구 호출 뒤와 턴 끝에만 실행되므로, 긴 명령이 도는 동안에는 결과가 있어도 표시되지 않습니다.
  - 메인 모델은 교정 결과를 보지 못합니다. 사용자가 방금 나온 교정에 대해 물어도 답할 수 없습니다.
  - 교정 프로세스는 프롬프트만 봅니다. 이전 대화나 `@파일`의 내용은 알지 못합니다.
  - 답변 언어는 훅이 강제할 수 없고 메인 모델의 지시 준수에 의존합니다. 기본값의 짧은 질의응답은 가끔 중국어로 답하고, `CHINESE_PROOFREAD_LANG=English`의 답변은 안정적이지 않습니다. 이 항목은 20번에서 최종 답변에 한해 해결했습니다.
  - 15번 항목은 교정 블록을 출력할 때만 답변 언어를 적용하도록 정했지만, 이제 시작 시점에는 교정 대상이 있는지 알 수 없습니다. 그래서 인용한 중국어인지는 메인 모델이 따로 판단합니다.
  - 한자가 들어간 프롬프트마다 Sonnet 호출이 한 번 더 듭니다.
  - 표시 앞에 `Stop says:` 같은 문구가 붙습니다. `설명:` 라벨은 설명 언어를 바꿔도 한국어로 남았지만, 이 문제는 20번에서 해결했습니다.
  - 플러그인이 켜져 있으면 중국어 입력이 아니어도 도구 호출마다 Python 프로세스가 한 번 실행됩니다.
- **결과**:
  - 대화형 시나리오 17개를 3회씩 실행한 51회에서 블록 수와 표시 시점이 모두 기대와 일치했습니다. 인터럽트와 권한 거부 뒤에도 블록을 잃지 않았습니다.
  - 전체 평가에서 작업 수행은 두 모델 모두 117/117이고, 메인 모델이 블록을 쓰거나 교정을 언급한 경우는 없었습니다. 교정 프로세스의 오류 검출은 45/45입니다. 자세한 결과는 `docs/eval-results.md`의 "#18: 병렬 교정"에 기록했습니다.

## 20. 중국어로 나온 최종 답변은 `Stop` 훅이 한 번 다시 쓰게 하고, `설명:` 라벨은 코드로 지운다

- **결정**:
  - `detect_chinese.py`는 중국어 프롬프트를 받으면 기대하는 답변 언어를 세션 폴더의 `reply-language` 파일에 기록합니다. 프롬프트가 들어올 때마다 이전 기록을 지우므로, 인터럽트된 턴의 기록이 다음 턴으로 넘어가지 않습니다.
  - `show_result.py`는 `Stop`에서 `last_assistant_message`를 읽습니다. 답변이 대부분 중국어이면 `decision: block`으로 턴을 이어 가게 하여, 기대하는 언어로 다시 쓰게 합니다. 기록을 먼저 지우므로 한 턴에서 다시 쓰기는 한 번뿐입니다.
  - 대부분 중국어라는 판정은 답변 전체를 기준으로 합니다. 코드 펜스와 백틱 안의 내용을 빼고, 한자가 10자 이상이며 한글 글자 수와 영어 단어 수의 합보다 많아야 합니다. 가나가 있으면 중국어로 보지 않습니다.
  - 다음 경우에는 답변 언어를 기록하지 않습니다.
    - `CHINESE_PROOFREAD_CHAT_LANG=prompt`로 설정한 경우
    - 답변 언어가 중국어인 경우
    - 프롬프트에 `中文`이나 `汉语`가 있는 경우
  - `proofread_worker.py`는 설명 언어가 한국어가 아니면 교정 블록에서 `설명:` 줄을 지웁니다.
- **이유**:
  - 대화형으로 실패를 재현한 결과, 프롬프트 4개를 두 언어 설정에서 5회씩 실행한 40회 중 3회가 중국어였고 모두 `一句话`가 들어간 프롬프트였습니다. 이 요청을 작업 결과물로 해석한다고 보고 지시문에서 설명은 결과물이 아니라고 명시했지만, 결과는 4/40으로 나아지지 않았습니다. 19번에서 문구와 순서를 여러 번 바꾼 기록까지 함께 보면, 지시문으로는 이 문제를 해결할 수 없다고 판단했습니다.
  - 19번은 답변 언어를 훅이 강제할 수 없다고 적었지만, 최종 답변에 한해서는 맞지 않습니다. `Stop` 훅은 transcript와 달리 `last_assistant_message`로 최종 답변을 바로 받습니다.
  - 판정을 줄 단위로 처음 구현했을 때는 긴 한국어 답변 끝에 중국어 문장을 인용한 경우와 일본어 답변이 걸렸습니다. 실제 실패는 답변 전체가 중국어이거나 중국어 뒤에 영어 설명이 붙은 경우뿐이었으므로, 답변 전체를 보도록 바꾸었습니다.
  - 라벨은 지시문으로 옮기라고 해도 안정되지 않았고 형식 점수가 떨어졌습니다(19번). 사용자가 어떤 언어 이름을 설정할지 알 수 없으므로, 번역을 코드에 넣는 대신 줄을 지웁니다. 다음 줄부터 나오는 항목만으로도 설명이라는 점을 알 수 있습니다.
- **대안**:
  - 지시문을 다시 고치는 방법은 위 측정에서 효과가 없었습니다.
  - 답변을 `PreToolUse`처럼 미리 막는 방법은 없습니다. `Stop`은 답변을 쓴 뒤에 실행되므로, 사용자가 처음 답변을 보는 것을 막지 못합니다.
  - 고치지 않고 README의 한계로 남기는 방법은, 잘못 읽으면 곤란한 작업 결과가 대상 사용자가 읽기 어려운 언어로 나올 수 있으므로 선택하지 않았습니다. 15번에서 답변 언어를 설정으로 분리한 이유와 같습니다.
  - 요청 의도를 모델에 물어 중국어 답변이 정당한지 판단하는 방법은, 턴마다 호출이 늘고 평가해야 할 대상이 늘어나므로 선택하지 않았습니다.
- **트레이드오프**:
  - 처음 쓴 중국어 답변이 화면에 남고, 그 아래에 `Stop hook error:`로 시작하는 영어 안내문이 나옵니다. 이 문구는 Claude Code가 정하므로 플러그인에서 바꿀 수 없습니다.
  - 다시 쓸 때마다 메인 모델 호출이 한 번 더 들고, 답변이 길면 같은 분량을 다시 씁니다.
  - 최종 답변만 확인하므로 작업 중의 진행 상황은 다시 쓰지 않습니다.
  - `中文`이나 `汉语` 없이 중국어 문구를 요청하면 지정한 언어로 다시 씁니다(`帮我写一句生日祝福的话` 2회 중 2회). 처음 쓴 문구는 화면에 남습니다.
  - 19번에서 `Stop` 재개 로직을 지운 뒤 턴을 잇는 동작이 다시 들어왔습니다. 다만 이번에는 교정이 아니라 답변 언어에만 쓰며, 기록 파일로 한 번만 실행합니다.
- **결과**:
  - 같은 40회 조건에서 최종 답변 언어는 37/40에서 40/40이 되었습니다. 최종 판정으로는 24회를 더 실행해 24/24였습니다. 자세한 결과는 `docs/eval-results.md`의 "대화 응답 언어 다시 쓰기"에 기록했습니다.
